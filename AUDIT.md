# Аудит WeddingCraft — 14 сентября 2026

Проверены основной Express API, Prisma-схема и история миграций, Next.js-приложение, редактор, кабинет, оплата, статические шаблоны, новая локальная студия и скрипты запуска/деплоя. Папки `edit` и `Wedding Invitation Website Homepage` — отдельные Vite-макеты; их манифесты и роль в проекте просмотрены, но отдельные production-сборки и браузерные сценарии этих макетов не проверялись.

Изменения внесены локально. Сервер, рабочие БД, платежи, DNS и внешние аккаунты не менялись. Незакоммиченные на начало проверки файлы студии сохранены; исправления безопасности внесены также в них. Это анализ кода с локальными проверками, а не пентест production-инфраструктуры.

## Исправлено

| Область | Проблема | Изменение |
|---|---|---|
| Вход | JWT принимал известный запасной ключ `secret`; отсутствовала проверка `userId` | Production требует ключ длиной минимум 32 символа, фиксирован HS256, проверяется субъект токена. В dev без подходящего ключа используется случайный ключ на время процесса |
| Код входа | Неограниченный перебор, `Math.random`, код в открытом виде в БД и логах | Криптографический генератор, HMAC в БД, ограничения по IP и email, атомарное однократное использование, проверка формата и нормализация email |
| Почта | Клиент получал «Код отправлен» даже при сбое отправки | API дожидается отправки, сообщает об ошибке и удаляет недоставленный код. Добавлены таймауты HTTP-провайдеров |
| Файлы | Доверие MIME из запроса и расширению имени позволяло сохранять HTML/SVG как загрузку | Белый список растровых изображений/аудио, проверка сигнатуры, расширение выбирает сервер, лимиты, удаление отклонённых файлов, `nosniff` и sandbox при отдаче |
| Шаблоны | Адрес изображения попадал в HTML без экранирования; ссылки принимали исполняемые схемы | Экранирование атрибутов, ограничения адресов, безопасная обработка ссылок во всех семи общих/статических runtime-файлах |
| Превью | Обработчики `postMessage` принимали чужие сообщения | Проверяются origin и окно-источник; отправка использует конкретный origin |
| Telegram | Не проверялся источник вебхука, ссылка подключения использовалась повторно | Секретный заголовок Telegram, атомарное погашение токена подключения, только личный чат |
| Уведомления | Гостевой текст вставлялся в HTML письма и трактовался как HTML в Telegram | HTML экранируется, Telegram получает обычный текст, содержание анкет не печатается в лог |
| RSVP | Повторный ответ по персональной ссылке создавал новую запись и увеличивал статистику | В транзакции заменяется ответ этого гостя. Чужие/неверные токены и ошибочные типы полей отклоняются |
| Кабинет | Приглашение с ответами нельзя было удалить из-за внешнего ключа | Ответы, гости и приглашение удаляются одной транзакцией с проверкой владельца |
| Публичный API | В публичном приглашении присутствовал `userId`; персональные имена можно было получить до публикации | Идентификатор владельца скрыт, резолв гостя требует опубликованного приглашения |
| Редактор | Создание черновика возвращало JSON-колонки строками; такие значения могли ломать поля | Новый черновик возвращает массивы/объекты. Добавлена серверная проверка структуры редактируемых данных |
| Адреса | Разрешались slug `privacy`, `oferta`, `studio`, конфликтующие со страницами | Адреса зарезервированы |
| Оплата | Без кассы dev автоматически публиковал сайт; PM2 запускал production как dev | Имитация требует одновременно `NODE_ENV=development` и `ALLOW_TEST_PAYMENTS=true`; PM2 запускает production-сборки. Исправлена проверка имени тарифа, добавлены таймауты и атомарная фиксация оплаты |
| Клиент | Временный сбой `/auth/me` удалял токен; страница успеха без id бесконечно ждала | Токен удаляется только при отказе в авторизации; отсутствие id переводит оплату в состояние ошибки |
| «Каллы» | Дефолтная подпись «Ваши Дарья и Вадим» перекрывала введённые имена | Подпись формируется из имён пары, произвольная пользовательская подпись сохраняется |
| Студия | Dev API без токена позволял читать/писать файлы и проксировать запросы | Токен обязателен, cross-origin запросы отклоняются, production возвращает 404 |
| Импорт студии | Доступ к внутренним адресам и исполнение чужого JavaScript на origin приложения | Публичный IPv4 проверяется и фиксируется на соединении, редиректы проверяются заново, лимит 8 MB, таймаут; CSP запрещает скрипты, формы и плагины |
| Публикация студии | `git commit` захватывал ранее подготовленные чужие изменения; push мог идти не из той ветки | Проверяются ветка и чистый индекс, коммит ограничен конкретными путями. Публикация в ходе аудита не запускалась |
| Сборка/деплой | Ошибки TypeScript игнорировались; изменения только lock-файла не переустанавливали зависимости | Проверка типов включена, `npm ci` и учёт lock-файла; имя backend-процесса согласовано с deploy-скриптом |
| БД | Последняя миграция не соответствовала текущей Prisma-схеме | Добавлена `20260914000000_complete_invitation_schema`; полный набор миграций проверен на новой SQLite БД |

Обновлены Next.js до 16.3.5, Axios до 1.20.0, Multer до 2.4.0, Nodemailer до 10.0.9 и уязвимые транзитивные зависимости. Для Prisma 6 использован адресный override `@prisma/config → deepmerge-ts ^8.0.0`; конфигурация Prisma и интеграционные тесты проверены после замены. При будущем обновлении Prisma этот override следует пересмотреть.

Защита загрузок сверена с [OWASP File Upload Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html), механизм секретного заголовка — с [Telegram Bot API](https://core.telegram.org/bots/api#setwebhook). Проверка сигнатуры не заменяет декодирование изображения и антивирусную проверку.

## Проверки

- `backend: npm test` — 10 успешных тестов: изолированная БД, полный набор миграций, HTTP-запросы к API, авторизация, OTP, RSVP, загрузки, удаление, блокировка имитации платежей.
- `backend: prisma validate` — успешно после обновления зависимостей.
- `frontend: npm run test:security` — 3 успешных теста: доступ к студии, внутренние IP/схемы URL, опасные значения полей во всех runtime-файлах шаблонов.
- Production-сборка Next.js и проверка TypeScript — успешно.
- ESLint исправленных runtime-обёрток и серверных модулей студии — успешно. Общий ESLint проекта всё ещё содержит ошибки в старых страницах: `any`, компоненты, объявленные внутри компонента, обновление state в эффектах. Правила основного приложения не отключались для получения зелёного результата; `require` разрешён только в новых CommonJS-тестах.
- `npm audit` после обновлений сообщил 0 известных уязвимостей в обоих основных проектах. Это результат базы npm на дату проверки, а не гарантия отсутствия всех уязвимостей.
- В браузере: заполнение стартовой анкеты, открытие редактора «Каллы», обновление места в iframe, персонализация имён/даты и исправленная нижняя подпись. Реальные отправка email/Telegram и оплата не выполнялись.

Для backend-тестов нужен Node.js с `node:sqlite` (проверено на Node.js 24). Сборщик Next.js предупреждает о широком tracing файлов в dev-модулях студии — отдельный пункт для оптимизации сборки.

## Перед выкладкой на сервер

1. Задать случайный `JWT_SECRET` минимум из 32 символов. Если прежний ключ был коротким или потенциально раскрыт, заменить его: старые сессии перестанут действовать. Старые ещё не использованные коды входа также потребуют повторной отправки из-за перехода на HMAC.
2. Проверить `NODE_ENV=production`, рабочие ключи кассы, почту и `FRONTEND_URL`. `ALLOW_TEST_PAYMENTS` на production не нужен и не разрешает имитацию. Для локальных тестов включать его только явно.
3. Перезапустить backend с корректной средой: он регистрирует Telegram-вебхук с секретом. `TELEGRAM_WEBHOOK_SECRET` можно задать отдельно; иначе он выводится из JWT-ключа. После смены секрета регистрация вебхука должна пройти успешно.
4. **Сначала резервная копия БД и проверка её схемы на копии.** На чистой БД применить `prisma migrate deploy`. Если действующая БД уже менялась через `db push`, новая миграция может конфликтовать с существующими колонками. Только после подтверждения полного совпадения схемы отметить соответствующую миграцию применённой через `prisma migrate resolve --applied 20260914000000_complete_invitation_schema`. Нельзя выполнять это вслепую или использовать `migrate reset` на рабочей БД.
5. Выполнить `npm ci`, генерацию Prisma Client и сборки; проверить PM2-процесс `wedding-api`. Существующий deploy-скрипт сам не выполняет миграции: этот шаг остаётся обязательным при изменениях схемы.
6. Для студии задать `STUDIO_TOKEN` в `frontend/.env.local`, даже при локальном запуске. Прокси теперь импортирует статическую разметку без исполнения JavaScript; полностью клиентские SPA могут не импортироваться в прежнем виде. Поддерживаются публичные IPv4-адреса и HTTP(S) на стандартных портах.

## Остаточные риски и дальнейшие работы

**Высокий приоритет:**

- Две SQLite БД и пять загруженных файлов уже отслеживаются Git. Добавленный `.gitignore` не удаляет их из прежних коммитов и индекса. Перед удалением из отслеживания перенести рабочие БД/загрузки за пределы checkout и сделать резервные копии: иначе последующий deploy может удалить эти файлы на сервере. При наличии персональных данных ограничить доступ к репозиторию и отдельно решить вопрос очистки истории. В ходе аудита эти файлы и история не удалялись.
- Один `paymentId` в приглашении не заменяет журнал платежей. Нужны отдельная таблица Payment, сохранённый ключ идемпотентности, повторное использование незавершённой оплаты, сверка суммы/валюты/тарифа, обработка отмен и возвратов. При одновременных запросах создания оплаты остаётся риск нескольких платёжных сессий.
- Кастомный домен сейчас можно зарезервировать без доказательства владения. Нужны DNS TXT challenge и уникальность домена на уровне БД; CORS и выдачу сертификата следует привязать к подтверждённому домену.
- Лимитеры работают в памяти одного процесса и сбрасываются при перезапуске. Для нескольких процессов и защиты от распределённых атак нужен общий storage и ограничения на reverse proxy. Анонимным загрузкам также нужны общий дисковый бюджет, срок жизни и удаление неиспользуемых файлов.
- JWT остаётся в localStorage. Следующий архитектурный шаг — HttpOnly cookie, защита CSRF и отзыв сессий. Защита от конкретных обнаруженных XSS уже добавлена, но полный аудит всех будущих импортированных шаблонов всё равно нужен.

**Надёжность и удобство:**

- Восстанавливать незавершённую стартовую анкету сразу после перезагрузки; сейчас анонимный черновик читается на этапе редактора, поэтому стартовая форма показывается заново.
- Хранить версии шаблонов: изменение общего `script.js` затрагивает все уже оплаченные сайты этого шаблона. Нужны preview, версия публикации и откат.
- Убрать создание вложенных React-компонентов в кабинете и закрыть оставшиеся ошибки ESLint без массового отключения правил. Затем добавить CI для сборок, тестов, миграций и аудита зависимостей.
- Собирать и запускать релизы в отдельных каталогах с переключением текущего релиза. Текущий deploy перемещает `.next` работающего сайта во время сборки и не откатывает весь релиз при ошибке backend.
- Отправлять уведомления через очередь с повторными попытками; сейчас RSVP сохраняется, но уведомление при внешнем сбое может потеряться.
- Для неперсональной ссылки по-прежнему можно отправить несколько ответов. Не дедуплицировать только по имени: совпадающие имена бывают у разных гостей. Лучше выдавать токен ответа для последующего редактирования.

## Предложения по развитию

1. **Редактирование после оплаты с историей версий.** Исправление времени или адреса — обычная потребность пары. Текущий запрет не менялся, поскольку это часть заявленной тарифной модели; рекомендую пересмотреть его и разрешить обновление текста с отдельной кнопкой публикации.
2. **Гости и семьи:** количество взрослых/детей, сопровождающие, ограничения питания, трансфер, отметка «ещё не ответил», экспорт для организатора. Разделять число ответов и фактическое число людей.
3. **Предпубликационная проверка:** имена, дата, адрес, карта, фото, мобильное превью, тестовая анкета и предупреждение о незаменённых демонстрационных текстах.
4. **Совместный доступ пары и организатора** с ролями: редактирование сайта, управление гостями, просмотр статистики.
5. **QR-код и добавление события в календарь**, маршрут до места, многоязычность приглашения.
6. **Сохранение работы:** явный статус автосохранения, восстановление после сбоя и черновики нескольких приглашений вместо единственного общего localStorage-ключа.

Наиболее полезный следующий этап: журнал платежей и резервное копирование, затем сохранение/редактирование после публикации и удобный кабинет гостей. Новые визуальные шаблоны стоит добавлять после стабилизации этих сценариев.
